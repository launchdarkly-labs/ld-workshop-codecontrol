# Same guard, real signal

In the Release track you shipped Chatty Otto behind a **guarded release**: LaunchDarkly ramped the new variation up gradually, watched a metric, and rolled back on its own when the metric regressed. You're about to do the exact same thing to the Personalized strategy, and the mechanism is identical, so this lab goes fast.

What's different is the metric. Last time the guard watched `otto-response-latency`, a number the app reported with a hand-written `track()` call. This time it watches **User HTTP error rate**, a metric LaunchDarkly generated from the instrumentation you added two labs ago. Nothing in the app knows this metric exists. The guard is watching the real error behavior of the service, not a signal someone remembered to emit.

The bug is still in Personalized, by the way. Nobody's fixed it. That's fine. Let's find out whether the guard catches it.

# Re-release Personalized, guarded

In the [LaunchDarkly](#tab-0) tab, open **recommendations-strategy**'s **Targeting** tab. The default rule serves **Bestsellers**, where you left it.

1. Edit the **default rule** and change the served variation to **Personalized**.
2. In the **Serve** menu, choose **Guarded rollout**.
3. Wait for the **health check** to turn green. It confirms the flag is receiving evaluations from `user` contexts and the metric is receiving events. Both have been true for a while thanks to the synthetic shoppers.
   <!-- VERIFY: health check wording/states ("Health check waiting" → "Healthy") and time to pass with lab traffic -->
4. Under metrics to monitor, add **User HTTP error rate**.
   <!-- VERIFY: the autogenerated metric's display name in the picker -->
5. Check **Automatic rollback** for the metric. Without it the guard only notifies.
6. Leave **Target by** on **user** (it must match the metric's analysis unit, which you read last lab), and set the **rollout duration** to the shortest schedule offered.
   <!-- VERIFY: default and minimum durations; capture the stage schedule shown -->
7. Click **Review and save**.

# Watch the guard work

The flag page shows the rollout monitoring: the share of shoppers on Personalized, the sample size on each side, and a tile for **User HTTP error rate** charting the *difference* between the new variation and the original. The shaded band is the confidence interval; for a lower-is-better metric, a regression is called the moment that whole band sits above zero.

![Monitoring the rollout](../assets/obs-06-monitoring.png)

Two things make this converge quickly here. Every synthetic shopper now browses the carousel, and about a third of them view the Rollout Tote, so the error rate on Personalized is large and steady, not subtle. And LaunchDarkly re-evaluates roughly every ten seconds. Still, it needs a minimum sample on each side before it will decide anything. If you're presenting (or impatient), open the terminal in the [Code Editor](#tab-2) tab and turn up the crowd:

```bash
python3 /opt/ld/codecontrol/traffic-generator/sabotage.py --target recs
```

That floods the carousel with shoppers, half of them viewing the tote. It fakes nothing: every error is the real bug firing, and the only thing you're accelerating is the statistics.

Then watch the metric tile. When the band clears zero, the tile flags a **regression**, and because you checked automatic rollback, LaunchDarkly **rolls the release back**: the default rule returns to **Bestsellers**, the rollout is marked regressed and rolled back, and the flag's maintainer is notified.

![Regression detected, rolled back](../assets/obs-06-rolled-back.png)

Confirm it in the [ToggleWear](#tab-1) tab: click the **Rollout Tote**; the carousel stays. Then look at the **Monitoring** tab's **Errors** chart one more time. The Personalized bar shows exactly how many shoppers were exposed during the ramp, and it stops cold at the rollback. That's the blast radius of this release, and it was bounded by a machine, not by whoever happened to be watching the dashboard.

# Why this is the better guard

Compare the two guarded releases you've run:

| | Release track (Otto) | This lab (carousel) |
|---|---|---|
| Metric | `otto-response-latency` | **User HTTP error rate** |
| Where it came from | A `track()` call you pasted | Generated from the server plugin's traces |
| What it can miss | Anything you didn't think to track | Nothing that fails a request |

The first kind of metric is only as good as the developer's imagination on the day they wrote it. The second kind watches the service itself. Once an app is instrumented, *every* release of *every* flag can be guarded on error rate and latency with zero extra code.

Click **Check** (a rolled-back rollout counts as success), then **Next**. One gap remains: a guard protects you while a release ramps. What protects a feature that's already at 100% when the world changes under it?
