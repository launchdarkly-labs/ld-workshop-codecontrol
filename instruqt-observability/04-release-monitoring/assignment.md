# How bad is it, in one number?

You've seen *that* Personalized throws and *who* it throws for. A release decision needs one more thing: a number that says how much worse the new variation is than the old one, measured the same way for both. That's a **metric**: a measurement your app reports to LaunchDarkly that can be compared across flag variations. You met one in the Release track (`otto-response-latency`), and you wired it by hand with a `track()` call.

This time you don't have to. The server plugin's request traces contain everything needed to compute error rates and latency per user, so LaunchDarkly **generates the metrics for you**. They've been quietly accumulating since you instrumented the app.

# Find the autogenerated metrics

In the [LaunchDarkly](#tab-0) tab, click **Metrics** in the left sidebar.

1. Look for metrics carrying the **autogenerated** tag. You should see a small family of them, all sourced from OpenTelemetry:
   <!-- VERIFY: exact metric names/keys as rendered in the Metrics list, and how long after the first trace they appear -->

   | Metric | What it measures |
   |---|---|
   | **User HTTP error rate** | Percentage of users who hit at least one failed request. |
   | **User HTTP 5XX response rate** | Percentage of users who got at least one 5XX response. |
   | **User non-HTTP exception rate** | Percentage of users who hit an exception outside a request. |
   | **Average / P95 / P99 request latency** | How long requests take, per request. |

2. Open **User HTTP error rate**. Read its definition: a *conversion* metric (did this user hit an error, yes or no), analyzed per **user**, where **lower is better**, and users with no events count as zero. Every one of those words will matter in the next lab.
3. Click **View**, then **Events**, to see the raw events arriving. Each one is a shopper whose request failed, and each carries the flag variation that shopper was served.
   <!-- VERIFY: the metric detail page's controls for viewing events ("View" → "Events" per the autogen-metrics doc) -->

![The autogenerated metrics](../assets/obs-04-autogen-metrics.png)

Two things to notice:

- **Lower is better** is not decoration. A guarded release decides what counts as a regression from the success criterion. An error metric accidentally marked "higher is better" would read a spike in errors as a successful release. The autogenerated metrics get this right for you.
- The analysis unit is **user**, which matches the `user` contexts your app sends. If your app evaluated flags with some other context kind, you'd edit the metric to match before relying on it. Ours already lines up.

# Read release health per variation

Go back to the **recommendations-strategy** flag's **Monitoring** tab and look at the **Errors** chart one more time, this time thinking in rates. Roughly a third of synthetic shoppers who view the carousel view the tote, so on **Personalized** about a third of browsing users hit the error; on **Bestsellers**, none. That gap is what **User HTTP error rate** measures, and it's exactly the signal a guard needs: a clear, honest difference between the new variation and the old one.

# Stop the bleeding

You have a diagnosis and a number. The right move now is the one you'd make in a real incident: revert, then re-release properly.

1. Open the flag's **Targeting** tab.
2. Edit the **default rule** and change it back to serve **Bestsellers**. Click **Review and save**.
3. In the [ToggleWear](#tab-1) tab, click the **Rollout Tote**. The carousel stays. Shoppers are safe again, and the error chart on the Monitoring tab will flatten over the next few minutes.

Click **Check**, then **Next**. This is the second time in this workshop a human had to notice a problem and flip a flag. Starting next lab, that stops being your job.
