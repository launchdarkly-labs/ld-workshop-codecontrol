# After the release is over

A guarded release has a blind spot by design: it only watches while the rollout is ramping. Once a variation reaches 100% and monitoring ends, nothing is looking at it anymore. And production doesn't stop changing. A dependency degrades, a catalog import adds a product with a missing field, traffic shifts to a code path nobody tested. The feature that was healthy on release day starts failing on day thirty, and the only safety net left is a human reading a dashboard.

An **adaptive trigger** closes that gap. You attach it to a flag rule and tell it: watch this metric, and if it crosses this threshold, switch the rule to this variation. LaunchDarkly then evaluates the metric continuously, for as long as the trigger exists, and when it fires, the flag changes and the people you named get an alert. It's the kill switch from the Release track, with LaunchDarkly's hand on it instead of yours.

This lab you'll arm one, then release Personalized to 100% the plain way, and let the trigger catch it.

# Arm the trigger

In the [LaunchDarkly](#tab-0) tab, open **recommendations-strategy**'s **Targeting** tab. The default rule should serve **Bestsellers**. If the guarded rollout from the last lab is still monitoring, click **Stop monitoring** and choose **Bestsellers** to serve.
<!-- VERIFY: "Stop monitoring" control location and dialog after a rolled-back rollout (it may already be finished, in which case this sentence is moot) -->

1. Under the **default rule**, click **Add adaptive trigger**.
   <!-- VERIFY: label and placement of "Add adaptive trigger" under the rule -->
2. In **Source**, choose **LaunchDarkly hosted metrics** and pick **User HTTP error rate**. If an **Analysis unit** menu appears, choose **user**.
   <!-- VERIFY: source dropdown labels; whether the autogenerated metric is offered here -->
3. In **Threshold**, set **Type** to **Constant**, **Condition** to **Above**, and the **Alert threshold** to:

   ```
   5
   ```

   That means "more than 5% of users hitting an error." Set the **Alert window** to the shortest option available.
   <!-- VERIFY: the unit the threshold field displays for this metric (percent?) and the available alert-window / cooldown option values -->
4. Under **Switch variation to**, choose **Bestsellers**.
5. (Optional) Click **+ Add notification** and add yourself.
6. Click **Add**. A summary of the trigger appears under the rule.

![The armed adaptive trigger](../assets/obs-07-trigger-config.png)

Nothing has changed for shoppers yet. The trigger is watching a flag that currently serves the safe variation, and the error rate is zero. That's the right order of operations: arm the safety net, *then* release.

# Release Personalized, the plain way

1. Edit the **default rule** and change the served variation to **Personalized**. No guarded rollout this time; just the variation.
2. Click **Review and save**.

You've now done the thing this track opened with, a plain release of a buggy variation to everyone. The difference is what's standing behind it.

# Let it heal

The synthetic shoppers are browsing, a third of them view the Rollout Tote, and every one of those on Personalized now generates an error. The **User HTTP error rate** climbs past 5% within a minute or two of traffic. If you want to hurry it along:

```bash
python3 /opt/ld/codecontrol/traffic-generator/sabotage.py --target recs
```

Then watch two places:

1. The flag's **Targeting** tab. When the trigger fires, the default rule flips itself back to **Bestsellers**. Reload the tab to see it, and note the change in the flag's history: it was made by the trigger, not by a person.
   <!-- VERIFY: how long from threshold breach to the switch with the shortest alert window; how the trigger's change is attributed in the flag history -->
2. **Telemetry → Alerts**. The trigger's alert is listed there with the flag name, the variation it switched to, and a chart of the error rate crossing the threshold.

![The trigger fired](../assets/obs-07-trigger-fired.png)

Confirm it in the [ToggleWear](#tab-1) tab: click the **Rollout Tote**. The carousel stays. Nobody flipped anything. The system noticed, decided, and reverted.

One more thing, if your account has **Vega**, LaunchDarkly's AI agent: open the alert and you may find it has already investigated, correlating the error spike with the flag change and pointing at the missing `category` field. The trigger heals the *symptom* by flipping the flag; Vega can draft the *fix* as a pull request. Both start from the same instrumented signal.

# Three safety nets

Step back and look at what ToggleWear has now:

| When | What watches | What happens |
|---|---|---|
| **During a release** | A guarded rollout | Regression detected, release rolled back |
| **After a release** | An adaptive trigger | Threshold crossed, variation switched |
| **Any time** | You, with the kill switch | Off, now |

The first two are the kill switch with the waiting removed. Both need the same two ingredients you built in this track: a flag around the behavior, and an honest signal about whether it's working. Instrument once, and every flag you own can defend itself.
